# v0.2.4 实施计划

设计依据：`../specs/2026-10-31-v0.2.4-design.md`，用户于 2026-10-31 确认可进入实施计划。
状态：用户已确认，代码与离线测试已实现；真实模型验收受 QUOTA / HTTP 402 阻塞，尚未发布。执行方式：当前会话单线程、分阶段实施，无需新建聊天或委派代理。当前验证见 `../../acceptance-v0.2.4.md`。

## 执行约束

- 复用现有仓库与 Harness 接口，不修改 sources/ 或 Harness 核心。
- 每阶段先为关键行为添加失败用例，再实现并运行对应测试；阶段通过后继续后续步骤，避免每阶段重复请求授权。
- 报告、证据、检查点兼容以内容哈希和版本为准。所有恢复生成新 runId，原文件保持不变。
- 不把 fixture 模型测试称为真实模型验收；不把提取覆盖称为语义准确率；不把未知用量记为零。
- GitHub/npm 发布已由原任务授权，测试通过后执行。登录、安全密钥或新增信任授权由用户完成。

## 1. 基线与宿主能力核查

检查 git 状态与远端 main/tag，确认 v0.2.4 未被其他发布占用。存在外部变更时先分析并保留，禁止重置覆盖。运行现有 npm test，保存测试基线。

读取实际本地 Harness 的 LLM 类型和适配器：prepareCall、usage 事件、输出上限、计费字段、输入 Token 计数能力，以及当前 Cordis/web 插件接口。将可用能力写入验收记录，不输出凭据。

验收：可定位实际服务实现；形成 Token 计数支持/不支持的证据；不假定新 API 存在。

## 2. 预算与用量基础层

修改 `lib/config.js`、`lib/model.js`，新增 `lib/budget.js` 和 `tests/budget.test.js`。

实现默认 64 次调用限制、可选总 Token 限制、阶段标签、调用预留/结算、失败计数与未知用量统计。调用预算检查放在统一模型入口，修复与复核不得绕过。验证每个统计字段来源，保留原始宿主 usage。

若真实宿主不支持可靠输入计数/上界及输出限制，配置总 Token 硬限制即返回 TOKEN_BUDGET_UNSUPPORTED，不发起模型调用；自动测试通过具备可信计数的假适配器验证硬限制路径，并明确这一测试范围。支持路由需验证输入预留、输出上限和并发预留边界。

验收：失败、修复和审核都占预算；次数到限时下一次调用为零；未知字段不当作零；不得以字符估计保证 Token 硬限制。

## 3. 章节识别与稳定抽样

修改 `lib/content.js`，新增 `lib/coverage.js`、`tests/coverage.test.js`，扩展 `tests/io.test.js`。

保留现有分块 ID/定位规则，在其上添加标题识别、章节区间和任务权重。维护可用、选中、已处理三套集合；分页或跨章片段可记录多个章节，不重复计入总片段。支持 unknown、缺失标题、小预算及全覆盖情况。存储分块参数和正文哈希。

验收：低预算优先覆盖重要章节；充足预算覆盖所有已识别正文类别；覆盖统计与成功证据提取一致；v0.2.3 样本的引用不发生静默漂移。

## 4. 工作流与可恢复状态

修改 `lib/workflow.js`、`lib/service.js`、`lib/storage.js`、`index.js`、`lib/web.js`，扩展 `tests/workflow.test.js`、`tests/lifecycle.test.js`。

引入 schemaVersion 3/promptVersion 0.2.4、研究模式、预算参数、budget-paused 状态、累计研究链账本。每个调用及阶段成功后保存进度；错误携带 key/runId 与可恢复原因。预算继续显式提高总额，普通重做创建新预算并说明区别。

补充研究只选已有材料中的未处理章节片段，复用哈希匹配证据，重新生成所选模块。失效的模块缓存不得保留。旧检查点读入后仅在新运行写入升级结果。新增写工具纳入沙箱权限、参数校验和同源保护。

验收：首次/中途超限均留下可恢复记录；恢复不重复成功调用；新增正文引入后模块重新生成；父版本字节不变；取消、网络失败与预算暂停可区分。

## 5. 证据审查和人工修订

新增 `lib/review.js`、`tests/review.test.js`；修改 `lib/analysis.js`、`prompts/analysis.md`、`index.js` 及归档层。

结论生成稳定 ID，保留原始分类。确定性规则拒绝无效引用并发现风险；模型复核仅检查高风险结论，批次有界、所有调用计费、每批结果检查点化。验证研究对象、数据集、对照、单位和前提字段；模型返回非法引用或改变分类时拒绝并保留未审核状态。

人工意见采用独立附加文件和修订日志，校验报告哈希、结论 ID、revision，支持确认/质疑/待复核与备注。人工确认不改变原事实类型、自动审查或原始报告。

验收：引用真实但超出原实验条件的性能/成本说法触发复核；推断/设想不能升级；未审高风险结论不显示有直接依据；冲突编辑可检测；预算暂停后复核可续。

## 6. 产品机会与草稿导出

新增 `lib/opportunities.js`、`tests/opportunities.test.js`；修改 `lib/modules.js`、`lib/analysis.js`、`lib/knowledge.js`、`lib/report.js`、`lib/report-format.js`、`prompts/analysis.md` 和工具导出参数。

定义卡片 schema 与来源校验，将机制、技术能力、产品能力、功能、用户旅程、假设、成本风险、指标、依赖、验收和 PoC 显式化。支持不建议采用及空卡片理由。保存模型建议与人工优先级的独立版本。

PRD/PoC 以确定性模板导出，不增加模型调用；保留原 product-ideas.md/poc.md。聚合时保留卡片所属论文与运行，避免跨论文伪造共同证据。

验收：每张卡片可溯源或明确为假设；草稿包含可执行验证和停止条件；不适用不会生成虚假收益；导出与人工调整不修改原报告。

## 7. 工作台交互与报告阅读

修改 `client/main.js`、`client/history-view.js`、`client/report-view.js`、`client/reading-model.js`、`client/reading-style.js`，必要时拆分覆盖/审查/卡片组件；扩展渲染回归测试。

添加模式预设及可修改模块、预算配置、阶段次数/耗时/用量。历史提供预算暂停及继续入口。报告展示章节处理覆盖、补充章节、结论审查与人工备注、机会优先级和草稿下载。

沿用现有阅读视觉结构与术语；旧报告缺失新字段时显示未记录，不触发模型请求。保留图表、证据跳转、源码及下载。输入均按不可信数据渲染。

验收：真实浏览器完成设置、暂停/恢复、补充、复核编辑和导出；旧报告可读；恶意 HTML、SVG、Mermaid、备注与下载文件名安全回归通过。运行 build:client 更新生成文件。

## 8. 完整验证与交付文档

更新 fixtures、host-smoke 和 verify-acceptance，避免用固定调用次数掩盖新增审查。运行 npm run check、npm run build:client、npm test、npm pack --dry-run；检查构建产物确定性。

在隔离的 Harness 测试配置上验收公开论文的真实检索/导入及真实模型分析，完成预算中断、继续、补充章节、复核记录与 PRD/PoC 导出；验证原先 27 个工具注册和既有调用兼容，检查新工具写权限及卸载。

保存本地报告、截图和结构化证据；公开 docs/acceptance-v0.2.4.md 仅包含已执行结果、公开例子、覆盖范围、模型与限制。不能运行的外部来源或宿主能力明确标注，不冒充通过。干净安装打包产物并做最小加载测试。

更新 README、配置与 API 文档、Release Notes、验收摘要，以及 package/lock 为 0.2.4。公开文档不含私有路径、凭据或真实账号会话数据。

## 9. GitHub 与 npm 发布

审查相关 diff、构建文件、版本一致性和包内容后提交并推送 main；等待 Node 22/24 CI 均通过，再创建/推送 v0.2.4 并执行现有 Release 工作流。下载 Release tgz、验收摘要和 SHA256SUMS，核对版本、包名与 SHA256。

仅发布这份已核验 tgz 到 npm。若 npm 要求用户登录或安全密钥验证，在具体授权页面交接；不绕过 2FA，不修改安全策略。独立 npm 工作流仅在现有授权足够且有必要时添加，缺少授权时沿用已验证的本地同包发布流程。

公开 registry 可查询到 0.2.4 后下载 npm tgz，核对与 Release 相同的 SHA256/integrity，再做干净安装与加载冒烟测试。版本已占用且内容不同则停止发布，报告冲突，不重新使用版本号。

最终交付：GitHub commit/tag/Release、npm 链接、主要变化、测试范围、实际报告例子和明确限制。用户的正式 web 配置升级与重启按该阶段明确授权执行；本计划的真实宿主测试优先使用隔离配置。

## 执行方法

推荐在当前会话按 1→9 顺序实施。阶段 2、3 完成后接入工作流；阶段 5、6 在工作流基础上展开；UI 使用稳定后的数据结构。阶段 8 为发布门禁，未通过不得发布。计划确认后连续推进，不为每次常规修改和测试重新请求确认；只在真实外部授权缺失或需求发生实质冲突时交接。
